# T-006: LoudnessMeter (BS.1770 / EBU R128)
- Owner: dsp-engineer

## Goal
Implement a real-time-safe `LoudnessMeter` in `source/dsp/` that runs on the audio thread. It must produce momentary, short-term and integrated loudness, loudness range, and the maximum momentary and short-term values, conforming to ITU-R BS.1770-4/-5, EBU R128, and EBU Tech 3341 and 3342.

## Design requirements
- **K-weighting.** Two biquads per channel. At every sample rate from 44.1 to 192 kHz, derive the coefficients from the analog prototype parameters with the bilinear transform. This is the libebur128 method: the shelf is defined by f0, gain and Q, and the RLB high-pass by f0 and Q. Cite the parameter values you use. At 48 kHz, the derived coefficients must match the BS.1770 table in T-002 section 3 within 1e-6.
  - Architect decision, 2026-09-28: do not follow T-002's alternative suggestion of resampling to 48 kHz. Resampling adds audio-thread CPU and complexity for no accuracy gain.
- **Block structure.** 100 ms sub-blocks. Momentary is the 400 ms window; short-term is the 3 s window.
- **Integrated loudness.** Absolute gate at −70 LUFS and relative gate at −10 LU, over 400 ms blocks with 75 % overlap. Use a fixed-size histogram (or another bounded-memory method recommended by T-002) so that the audio thread does no allocation and no unbounded loops, and the result is exact within the Tech 3341 tolerance.
- **LRA.** Follow EBU Tech 3342: short-term values with a −70 LUFS absolute gate and a −20 LU relative gate, then the 10th to 95th percentile. Use bounded memory.
- **Channel weights.** L and R are 1.0; mono is 1.0.
- **API.** `prepare(sampleRate, maxBlockSize, numChannels)`, `process(const float* const* channels, int numChannels, int numSamples) noexcept`, `reset()`, and value getters. Everything is allocation-free after `prepare`.
- **Before data exists.** Until enough data exists, values report negative infinity or a documented sentinel. They never report NaN.
- **Test oracle.** T-021 links libebur128 (MIT) into the unit test target only. Ask unit-tester to cross-check M, S, I and LRA against it on 60 s of pink noise and on a stepped-level signal.
- **Test-case values.** The EBU test-case table in T-002 is only a summary and is partly inaccurate. The exact expected values and tolerances for every Tech 3341 and Tech 3342 case must be transcribed from the official EBU documents (Tech 3341 and Tech 3342, current versions). Call researcher to fetch and transcribe them into `docs/research/T-006-ebu-test-cases.md`, a folder researcher owns. Tests use those transcribed values, citing the case numbers.
- **Official files.** Not used (user decision, 2026-09-28). Cases that need the official audio are listed as "not run (official file required)" in the QA report. The libebur128 cross-check covers that ground instead. Do not write tests that depend on `INVESTIGATE_EBU_TEST_SET_DIR`.

## Acceptance criteria
- [ ] Every EBU Tech 3341 case marked "synthesisable" in the T-002 table passes within the standard's tolerance: ±0.1 LU for M, S and I, unless the standard states otherwise.
- [ ] Every EBU Tech 3342 case marked "synthesisable" passes within ±1 LU.
- [ ] Cases that need the official files are listed in the QA report as not run, with the reason (a user decision).
- [ ] A 1 kHz sine at −23 dBFS on both channels of a stereo input reads −23.0 ±0.1 LUFS for M, S and I after 3 s. On a mono input with the same sine it reads −26.0 ±0.1 LUFS, following BS.1770's single-channel weight.
- [ ] The K-weighting frequency response at 44.1, 88.2, 96 and 192 kHz matches the 48 kHz response within ±0.1 dB from 20 Hz to 16 kHz. The derived 48 kHz coefficients match the BS.1770 table within 1e-6.
- [ ] The libebur128 cross-check agrees within ±0.05 LU for I and M, and ±0.1 LU for S and LRA, on the signals named in the design requirements, at 44.1, 48 and 96 kHz.
- [ ] `process` performs no allocation (verified by unit-tester's allocation check) and has no data-dependent unbounded loops.
- [ ] `process` takes ≤ 5 µs mean per 128-sample stereo block at 48 kHz in Release on the development machine.
- [ ] After `reset()`, the integrated loudness, LRA and max values restart. A 1-hour simulated run (fed faster than real time) keeps memory constant and the integrated value stable within ±0.01 LU on a stationary signal.
- [ ] Warning-clean at `/W4`. `docs/qa/T-006-unit.md` reports PASS.

- 2026-09-28 dsp-engineer: Design, before coding (per CLAUDE.md step 1):
  - **K-weighting.** BS.1770 Annex 1's two-stage filter (high-shelf pre-filter + RLB high-pass), each stage an analog prototype (f0, gain, Q) converted per sample rate via the bilinear transform - the libebur128 method, not resampling (architect decision). Read `third_party/libebur128-src/ebur128/ebur128.c` (`ebur128_init_filter`) directly to get the exact prototype parameters libebur128 uses (shelf: f0=1681.9744509555319 Hz, gain=3.999843853973347 dB, Q=0.7071752369554196, plus the Vb exponent 0.4996667741545416; RLB: f0=38.13547087602444 Hz, Q=0.5003270373238773). Verified numerically (Python, see task transcript) that these reproduce the BS.1770-4 §5.4 48 kHz table (b0=1.53512485958697, b1=-2.69169618940638, b2=1.19839281085285, a1=-1.69065929318241, a2=0.73248077421585 for the shelf; b0=1, b1=-2, b2=1, a1=-1.99004745483398, a2=0.99007225036621 for the RLB) to a difference on the order of 1e-15 - well inside the 1e-6 acceptance criterion. Implemented as two cascaded Direct-Form-I biquads per channel, double precision throughout (coefficients and state), per CLAUDE.md's "double where precision matters" rule (the RLB pole sits close to DC).
  - **Block structure.** 100 ms sub-blocks (`round(sampleRate * 0.1)` samples). Momentary = sliding sum of the last 4 sub-blocks (400 ms); short-term = sliding sum of the last 30 (3 s); each its own small fixed-size ring buffer (4 and 30 doubles) so the two windows don't need shared-array index arithmetic. Loudness formula: BS.1770 eq. (2), `L = -0.691 + 10*log10(sum of per-channel mean square)` - a *sum*, not an average, across channels, each weighted 1.0 (L, R and mono are all 1.0 per the task; Investigate never analyses the surround channels BS.1770 weights at 1.41). This sum (not average) is what produces the acceptance criterion's ~3 dB (10*log10(2)) gap between an identical stereo and mono sine.
  - **Integrated loudness and LRA gating.** Read `ebur128.c`'s `ebur128_init_filter` histogram setup, `ebur128_gated_loudness` and `ebur128_loudness_range_multiple` (histogram branch) directly to replicate libebur128's own `EBUR128_MODE_HISTOGRAM` technique bit-for-bit in structure: a fixed 1000-bin, 0.1 LU histogram spanning [-70.0, +30.0) LUFS, using each bin's *centre* energy (not the actual per-block energy) as every block's representative value - this is what keeps the algorithm O(1) memory instead of storing every block. Two such histograms (Integrated, LRA), each with a running total count. Both gating passes (absolute gate at collection time, relative-gate mean/threshold/re-sum at read time) replicate libebur128's exact rounding convention (advance the relative-gate start bin by one if the threshold value sits above that bin's own centre energy) so the cross-check has the best chance of landing well inside its tolerance rather than just inside it. LRA's percentile step replicates `ebur128_loudness_range_multiple`'s rank formula exactly: `rank = floor((gatedCount-1)*percentile + 0.5)`, walking the histogram bins in ascending order accumulating counts until the cumulative count exceeds the rank, for P=10 and P=95 (continuing the bin cursor forward between the two, as libebur128 does, since the histogram is already sorted).
  - **Recompute cost.** `getIntegratedLoudness()`/`getLoudnessRange()` are O(1) getters; the two-pass 1000-bin gating scan happens inside `onSubBlockComplete()`, at most once per 100 ms sub-block - not per `process()` call and not per audio block - since MeterBank (T-007) is expected to read these every `processBlock` for the snapshot, and Integrated/LRA are only meaningful at 100 ms granularity anyway. Keeps the audio-thread cost of the (still fully bounded, ~1000-iteration) histogram passes off the per-block hot path.
  - **Sentinels.** `negativeInfinity()` for M, S, I and the max-M/max-S getters before enough data exists (never NaN - `energyToLoudness` explicitly guards `log10(0)`). `getLoudnessRange()` reads 0.0 before any value has passed both its gates, matching libebur128's own sentinel (LRA is a non-negative range; -inf would misleadingly suggest "extremely narrow" rather than "no data yet") - documented as a deliberate deviation from the "or a documented sentinel" wording in the task.
  - **API.** `prepare(sampleRate, maxBlockSize, numChannels)`, `reset() noexcept`, `process(const float* const* channels, int numChannels, int numSamples) noexcept`, plain-value getters - no APVTS, no JUCE dependency at all (only `<array>`, `<vector>`, `<cmath>`, `<algorithm>`, `<limits>`, `<cstdint>`), so it is trivially testable standalone. `numChannels` passed to `process()` is clamped to the count passed to `prepare()` to avoid any out-of-range access; a mismatch is not expected in normal use (the roadmap re-prepares every meter on a bus-layout change), so this clamp is a safety net, not a supported "reconfigure per block" path.
  - **Denormals.** Followed `SpectrumAnalyser`'s precedent (no per-class `juce::ScopedNoDenormals`) rather than adding a JUCE dependency just for that - documented in the class comment as an assumption that the caller (the processor, per the roadmap's architecture table) has it active for the duration of `process()`. Flagged in this report's open questions for unit-tester's real-time-safety audit to confirm it's comfortable with that assumption for a class that calls itself "testable without a plugin instance".

- 2026-09-28 dsp-engineer (round 2 fix): Diagnosed that the 100 ms grid was overloaded for two different purposes - Integrated Loudness/LRA gating, where BS.1770 Annex 2 *requires* an exact 100 ms hop (75% overlap of the 400 ms block) as part of the algorithm itself, and Momentary/Short-term's own sliding-window update resolution, which the standard leaves as an implementation freedom (only a ≥10 Hz *display* rate is mandated).
