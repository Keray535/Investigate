# T-007: Level, true-peak and correlation meters, MeterBank
- Owner: dsp-engineer
- Milestone: M1
- Status: DONE
- Depends on: T-006

## Goal
Implement the remaining audio-thread meters in `source/dsp/`: `LevelMeter`, `TruePeakDetector` and `CorrelationMeter`. Then add a `MeterBank` that owns all meters, including the `LoudnessMeter` from T-006. `MeterBank` publishes a `MeterSnapshot` lock-free for any thread to read, and handles reset requests from the message thread.

## Inputs
- `docs/roadmap.md`: the Architecture sections (signal flow, modules table, MeterSnapshot contents, parameter table: `rmsWindow` and `meterScale`, threading model) and Budgets.
- `docs/research/T-002-dsp-references.md`: sections 4 (true peak), 5 (correlation), 6 (K-system and RMS) and 7 (atomics for the snapshot).

## Design requirements
- **`LevelMeter`.**
  - Per-channel sample peak for the current block, and a peak max held since the last reset.
  - RMS over `rmsWindow` (50 to 3000 ms). Preallocate for 3000 ms at 192 kHz, or use the bounded method T-002 recommends.
  - A sample clip counter: it counts samples with |x| ≥ 1.0 (0 dBFS), as in SPAN (T-001 section 3).
  - RMS is reported unreferenced: a full-scale sine gives −3.01 dBFS. The editor applies the AES17 and K-system offsets.
  - Use a true sliding window, as T-002 section 6 recommends. Guard against accumulator drift in the running sum: use a double accumulator, periodic exact recomputation, or sub-block partial sums. A test must show no drift after 1 hour of simulated audio.
- **`TruePeakDetector`.**
  - A BS.1770 Annex 2 polyphase FIR.
  - Oversampling per T-002 section 4: 4x at 44.1 and 48 kHz, 2x at 88.2 and 96 kHz, and 1x (sample peak) at 176.4 and 192 kHz. Take the 48-tap, 4-phase filter coefficients from the BS.1770-5 Annex 2 text, with a citation. For 2x, use the appropriate subset of phases, or a filter justified in a code comment.
  - The exact true-peak case values come from `docs/research/T-006-ebu-test-cases.md`, which T-006 produces.
  - Reports the current true peak and the true-peak max since the last reset.
  - A true-peak clip counter: it counts input samples whose interpolated neighbourhood reaches or exceeds 1.0 (0 dBTP). This equals SPAN's "True Peak Clippings" (T-001 section 3). Document the exact rule in a comment.
- **`CorrelationMeter`.**
  - Normalised cross-correlation over a 500 ms averaging window, matching SPAN's documented "500 ms average" (T-001 section 3; roadmap Decisions). Either of these is acceptable, documented in a comment:
    - a rectangular 500 ms window built from sub-block partial sums (for example 10 ms sub-blocks in a fixed ring);
    - three exponentially smoothed sums (ΣLR, ΣL², ΣR²) with a time constant chosen so the step response matches a 500 ms rectangular window at its midpoint.
  - L/R balance: 10·log10(ΣR² / ΣL²) over a 3 s window, so a negative value means the left channel is louder. Use the same sub-block technique.
  - Silence reports a correlation of 0 and a balance of 0 dB, never NaN. Clamp the denominators with an epsilon, as T-002 recommends.
  - A mono input reports a correlation of +1 and a balance of 0 dB, and sets `isMono`.
- **`MeterSnapshot`.** The plain struct listed in the roadmap:
  - per channel: peak, peak max, RMS, true peak, TP max, sample clip count and true-peak clip count;
  - loudness M, S, I, LRA, M max and S max;
  - correlation, L/R balance, `isMono`, the sample rate, and `blockCounter`.
- **Display-rate peaks.** `samplePeak` and `truePeak` are the maximum over the last 50 ms, not over the current block. The editor reads at 30 to 60 Hz and must not miss peaks. Use a small fixed ring of sub-block maxima.
- **`blockCounter`.** Incremented on every `process` call, so the editor can tell when the host has stopped calling it.
- **`MeterBank`.**
  - `prepare(sampleRate, maxBlockSize, numChannels)`.
  - `process(const float* const*, int numChannels, int numSamples) noexcept`.
  - `setRmsWindowMs(float)`, which is real-time safe.
  - `requestReset()`, callable from any thread. It sets an atomic flag that `process` consumes at the start of the next block. It resets peak max, TP max, both clip counts, integrated loudness, LRA, M max and S max.
  - `getSnapshot() const noexcept`, readable from any thread. Follow T-002 section 7, option (a): a double-buffered snapshot, published with a release store of the index and read with an acquire load. Document why a reader cannot observe a slot while the writer is rewriting it. If the design cannot guarantee that, use a seqlock-style version counter with retry on the reader side; the reader runs on a non-real-time thread, so retrying is acceptable there.

## Acceptance criteria
- [ ] The snapshot's sample peak equals the exact maximum |x| over the last 50 ms (±1 block of granularity). A single full-scale click inside a 128-sample block stays visible in the snapshot for at least 50 ms. Peak max holds until reset. `blockCounter` increases by exactly 1 per `process` call.
- [ ] RMS of a sine at −6 dBFS reads −9.03 ±0.05 dB after one window length plus 10 %, for `rmsWindow` values of 50, 300 and 3000 ms at 44.1 and 192 kHz.
- [ ] True peak: a sine at fs/4 with a 45° phase offset and a sample peak of −3.01 dBFS (a 0 dBFS true peak) reads a sample peak of −3.01 ±0.01 dB and a true peak of 0.0 dB, within +0.2/−0.4 dB. Every EBU Tech 3341 true-peak case, 15 to 23, passes within +0.2/−0.4 dB at 48 kHz. Take the definitions and expected values from `docs/research/T-006-ebu-test-cases.md`. Cases 20 to 23 must be synthesised as that file describes: generated at 4·fs, anti-alias filtered, then downsampled with sample offsets 0 to 3.
- [ ] True-peak cross-check: on 60 s of full-scale-normalised pink noise, on a swept sine from 20 Hz to 20 kHz, and on the fs/4 45° case, at 44.1, 48 and 96 kHz, the true-peak max agrees with libebur128's `EBUR128_MODE_TRUE_PEAK` result within ±0.2 dB. libebur128 is linked into the unit tests only (T-021). This replaces the official EBU true-peak files, which the user decided not to use.
- [ ] The sample clip count equals the exact number of samples with |x| ≥ 1.0 in a generated test signal. The true-peak clip count is ≥ 1 for the fs/4, 45° case scaled to a true peak of +0.5 dBTP with every sample below 1.0, and it is 0 when the same signal is scaled to a true peak of −0.5 dBTP.
- [ ] Correlation: L = R gives +1.00 ±0.01. L = −R gives −1.00 ±0.01. Independent white noise gives |r| ≤ 0.05 after 1 s. Silence gives 0.00 and never NaN. A 90° phase-shifted sine pair gives 0.00 ±0.02. After a switch from L = R to L = −R, the reading crosses 0 at 250 ±50 ms and reaches −0.95 or lower by 600 ms.
- [ ] Balance: L at −6 dBFS with R at −12 dBFS (both noise) gives −6.0 ±0.2 dB after 3 s. Equal levels give 0.0 ±0.2 dB. Silence gives 0.0 and never NaN.
- [ ] A reset requested from another thread takes effect at the next `process` call. No data race is reported (the test runs the reset from a second thread).
- [ ] `MeterBank::process` performs no allocation. It takes ≤ 15 µs mean and ≤ 40 µs p99 per 128-sample stereo block at 48 kHz in Release on the development machine.
- [ ] No NaN or Inf in the snapshot for silence, DC, full-scale noise or denormal-range input.
- [ ] Warning-clean at `/W4`. `docs/qa/T-007-unit.md` reports PASS.

  - **`LevelMeter`**: per channel (max 2), a single 10 ms sub-block cadence (matching `LoudnessMeter`'s pattern, `subBlockSamples = round(sampleRate*0.01)`) drives two independent, *exact-recompute* (no incremental-sum drift) mechanisms: (1) a 5-slot ring of per-sub-block linear peak maxima (5x10ms = 50 ms) for the display peak - satisfies "≤1 block granularity, visible ≥50 ms"; (2) a 300-slot ring of per-sub-block sum-of-squares (300x10ms = 3000 ms, the max `rmsWindow`) for RMS - `getRmsDb` sums the last `round(windowMs/10)` ring entries fresh every sub-block boundary (bounded ≤300 iterations, cheap, and *provably drift-free* since it is a full recompute each time, not a running add/subtract - satisfies "no drift after 1 hour"). `peakMax` and `sampleClipCount` update every sample directly (already computing `abs(x)` for the sub-block peak, no extra cost) and are cleared only by `resetStatistics()`, never by `reset()`'s sibling sub-block/ring state alone - `reset()` (full, used by `prepare()`) clears everything, `resetStatistics()` (used by `MeterBank::requestReset()`) clears only `peakMax`/`sampleClipCount`, leaving the RMS window and the 50 ms display ring rolling (roadmap: RMS and the 50 ms peaks are not "since reset" quantities). `setRmsWindowMs` is a single `std::atomic<float>` store, real-time-safe from any thread.
  - **`TruePeakDetector`**: BS.1770-5 Annex 2 48-tap/4-phase polyphase FIR at 4x (44.1/48 kHz), a 2-phase subset at 2x (88.2/96 kHz), and direct sample peak (no filtering) at 1x (176.4/192 kHz) - factor chosen by `sampleRate <= 48000+eps -> 4`, `<= 96000+eps -> 2`, else `1`. For each input sample, compute all active oversample phases from a 12-tap delay line, take the max |value| as that sample's "true-peak neighbourhood" value: feeds the same 50 ms-ring/peak-max/dB pattern as `LevelMeter`, plus the true-peak clip counter (once per *input* sample, not per oversampled point, when the neighbourhood max reaches 1.0). Exact coefficients are being transcribed by `researcher` from the ITU-R BS.1770-5 PDF into `docs/research/T-007-true-peak-coefficients.md` (dispatched before this log entry) rather than typed from memory, per the task's citation requirement; implementation is blocked on that report only for the coefficient table, everything else above is written now. `resetStatistics()` clears only TP max/clip count, never the FIR delay line (avoids an artificial transient on a stats reset).
  - **`CorrelationMeter`**: rectangular-window sub-block-partial-sum technique (roadmap's first documented option), one 10 ms cadence shared by both windows: a single 300-slot ring of `(sumLR, sumL2, sumR2)` per sub-block (300x10ms = 3 s, the longer of the two windows). Correlation sums the last 50 ring entries (500 ms) and balance sums all 300 (3 s), both recomputed fresh once per `process()` call (bounded ≤350 additions total, not per-sample or per-sub-block) - so, like the RMS design, no incremental-sum drift is possible. Denominators are epsilon-clamped (`1e-20`, negligible next to any real signal's sum-of-squares but eliminates 0/0): silence and "no data yet" both naturally evaluate to exactly correlation 0.0 and balance 0.0 with no special-casing. Mono (`numChannels < 2`) short-circuits to correlation +1, balance 0, `isMono` true, with no accumulation. `MeterBank::requestReset()` does not touch this meter (roadmap: correlation/balance are continuous 500 ms/3 s readouts, not "since reset" quantities).
  - **`MeterSnapshot`**: plain struct (all `std::array`/scalar fields, trivially copyable, no owned memory) with the fields the roadmap's "MeterSnapshot contents" section lists; `-inf` sentinels via `Decibels::negativeInfinityDb()`.
  - **`MeterBank`**: owns all four meters (`LevelMeter`, `TruePeakDetector`, `LoudnessMeter`, `CorrelationMeter`). `requestReset()` is a single `std::atomic<bool>` store (any thread); `process()` consumes it first (atomic exchange) and calls each meter's `resetStatistics()` (added a new `resetStatistics()` method to `LoudnessMeter` for this - see below), matching the roadmap's exact reset list (peak max, TP max, both clip counts, integrated loudness, LRA, M max, S max - *not* RMS, momentary, short-term, or correlation/balance). Publishing uses a **seqlock** (version counter, odd = write in progress / even = stable, acquire/release-fenced), not a plain two-slot double buffer: with only two buffers and a single atomic index, nothing stops the audio thread from starting to overwrite a buffer a slow/preempted reader is still mid-copying from (the buffer "laps" the reader) - the task's own fallback clause ("if the design cannot guarantee that, use a seqlock-style version counter with retry") is used because that guarantee cannot be made in general (a reader can stall for an arbitrary, unbounded time). The seqlock's retry-until-stable-version protocol is correct for *any* reader stall duration, at the cost of a cheap spin-retry on the reader (non-real-time thread), which the task explicitly allows.
  - **`LoudnessMeter` change**: adding `void resetStatistics() noexcept` (clears `integratedHistogram`/`Total`, `lraHistogram`/`Total`, `integratedLoudness`, `loudnessRange`, `maxMomentary`, `maxShortTerm` only - leaves K-weighting filter state, the momentary/short-term sliding rings, and their current values untouched).
