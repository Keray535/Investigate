# T-039: Spectrum engine: pan margin and bin spacing in the frame
- Owner: dsp-engineer
- Milestone: M3b
- Status: DONE
- Depends on: T-035 (and T-036 for build order only: one C++ task at a time)

## Goal
Make each zoomed frame carry curve points for a margin beyond the visible view, so that a fast pan or a zoom-out does not show an empty strip at the leading edge while the editor waits for the re-mapped frame. Also make each frame carry the bin spacing of the data it was mapped from, so the zoom panel's bin-spacing row is correct while frozen and just after a block-size change. These close open questions 5 and 6 of `docs/design/ui-spec.md` §15, which the architect accepted on 2026-10-03.

## Scope
1. **Pan margin.** For a clamped view `[vLo, vHi]` with `N` visible points and the log step `step = log2 (vHi / vLo) / (N − 1)`:
   - extend the published grid by `m = lround (0.25 × (N − 1))` points on each side, so the margin covers 25 % of the visible span in octaves per side;
   - clip each side's margin to the effective home range (fewer points on that side, never a point outside the home range);
   - **extend the same grid; do not re-space it.** Compute every point as `log2 (vLo) + step × k` for `k` from `−mLo` to `N − 1 + mHi`, with exactly the T-035 arithmetic for the visible `k`, so the visible points stay bit-identical to the T-035 output;
   - the smoothing padding from T-035 is applied beyond the margin, still clipped to the home range;
   - snapshot re-maps (while frozen) carry the margin too.
   At Fit both margins are 0, so the output is bit-identical to today.
2. **Frame fields.**
   - `numPoints` becomes the total published point count, margin included. Add `firstVisiblePoint` and `numVisiblePoints` so the editor can find the visible part without searching. `viewFreqLow` and `viewFreqHigh` keep their meaning (the clamped view).
   - Raise the point capacity to 3072 (`2048 + 2 × 512`), so `N = 2048` with both margins fits. Update the size comment and add a `static_assert` that ties the capacity to the maximum `N`.
   - Add `double binHz`: the bin spacing of the data the frame was mapped from (sample rate / block size). Frozen frames carry the snapshot's value, so a block-size change while frozen does not change it.
3. **Overview:** unchanged.
4. Keep the existing processor and editor building and passing unchanged. The editor never sets a view before T-037, so it never receives margin points. Do not edit `source/PluginProcessor.*` or `source/gui/`.

## Acceptance criteria
- [x] **No regression at Fit.** With no view set, the published frames are bit-identical to the T-035 output in every channel mode and smoothing mode, with `firstVisiblePoint = 0` and `numVisiblePoints = numPoints`. Every existing test passes; tests change only where they assert the new fields or the new capacity.
- [x] **Visible points unchanged.** For at least 20 zoomed views (spans from 1/6 octave to the home range, at the low edge, the high edge and inside), the visible points (`freqHz` and every active curve) are bit-identical to the T-035 output for the same view.
- [x] **Margin geometry.**
  - The published points span `[max (homeLo, vLo / 2^(0.25 S)), min (homeHi, vHi × 2^(0.25 S))]`, where S is the visible span in octaves, within one grid step.
  - The margin step equals the visible step within 1e-9 relative.
  - No point lies outside the effective home range, and the points are strictly increasing.
  - At most 3072 points are published.
- [x] **Margin values.** The margin points match a frame mapped for a view shifted so that they are visible, within 0.05 dB (aligned grid and signals several bins wide, as in the T-035 edge-smoothing test).
- [x] **binHz.** Live frames carry sample rate / block size. A frozen frame keeps the freeze-time value after a block-size change while frozen. Unfreezing publishes the new value.
- [x] **Allocation:** 0 allocations across freeze, unfreeze, view changes and re-publishes, as in the T-035 test.
- [x] **Timing (`[.perf]`):** the T-035 worst case with the margin included (dual mode, both secondary curves, sidechain, 1/3-octave smoothing, minimum span, `fftSize` 65536, plus the overview) takes ≤ 1.0 ms per re-map, as a median over 100 runs.

- 2026-10-03 dsp-engineer: Implemented (status IN_REVIEW, handed to unit-tester).
  - **Algorithm and expected behaviour (written before coding).** For the clamped view `[vLo, vHi]` with `N` visible points, `step = log2 (vHi / vLo) / (N - 1)` and `m = lround (0.25 (N - 1))`, the published grid is `exp2 (log2 (vLo) + step * k)` for `k = -mLo .. N - 1 + mHi`, with `mLo = min (m, stepsBelow)`, `mHi = min (m, stepsAbove)`, where `stepsBelow/Above = floor ((distance to the home edge in octaves) / step + 1e-9)` (the T-035 slack). So no point lies outside the home range, and with the view on a home edge that side has no margin; at Fit both are 0. The visible points use exactly the T-035 arithmetic (same exponent expression, same edges, same prefix-sum base), so they are bit-identical. The margin points are smoothed with the same boxcar; the padding continues beyond the margin by `half` points, clipped to the home range, so a margin point equals the same point of a frame mapped for a shifted view in which it is visible (home-edge truncation included). Expected cost: about +17 % raw points in the worst case (3 x 2048 + 2 x 512 array points against 3 x 2048).
  - **Bit-identity technique.** The array is `[-A, N - 1 + B]` with `A = min (m + half, stepsBelow)`. (1) The visible points' boxcar uses its own prefix sum starting at the first point of the T-035 padded range (`visPadLow = min (half, stepsBelow)`), with its own clamp indices, so the double sums are the same operations in the same order as before, independent of the margin. (2) The margin points use a second prefix sum over the whole array. (3) The single edge that closes the T-035 padded range (`j = N + visPadHigh`) keeps the T-035 formula `exp2 (logHi + step * (visPadHigh + 0.5))`; every other edge uses `logLo + step * (j - 0.5)`; this is what makes the last visible smoothing point bit-identical when a margin continues beyond it. Verified against a copy of the HEAD (T-035) mapper (see Verification).
  - **Frame (`SpectrumFrame.h`).** New `maxVisiblePoints = 2048`, `maxMarginPoints = 512`, `maxPoints = 3072` (`maxVisiblePoints + 2 * maxMarginPoints`), with `static_assert`s that tie the capacity to the maximum `N` (`spectrumMarginPointsFor (N) = (N + 1) / 4` for `N > 1`, the integer form of `lround (0.25 (N - 1))`; it is a namespace-level constexpr function because a member function cannot be used in the class's own constants). New fields `firstVisiblePoint`, `numVisiblePoints`, `double binHz` (0 when unset). `numPoints` is the total published count. **`sizeof (SpectrumFrame)` = 75848 bytes** (was about 51 KB; `FrameExchange` holds three slots, the processor copies one more, all well within budget; no 2048 array size is assumed anywhere in `source/`, grep done).
  - **Mapper API.** The T-035 API (`computeFrequencies`, `mapCurve`, `mapOverview`) is unchanged in behaviour: it still writes the visible points only (margin disabled), so every existing T-035 test passes unchanged. New for the engine: `computeFrameFrequencies (settings, out, numVisible)` returns `FrameLayout { numPoints, firstVisible, numVisible }` and `mapCurveFrame (...)`, which write margin plus visible. The grid cache key gained a `withMargin` flag, so alternating the two APIs rebuilds the grid correctly (checked). `SpectrumMapper::maxPoints` is now `SpectrumFrame::maxVisiblePoints` (the cap for `N`); `maxPaddedPoints = 3 * 2048 + 2 * 512 = 7168`.
  - **Engine.** `publishFrame` uses the frame API, fills `numPoints`, `firstVisiblePoint`, `numVisiblePoints` and `binHz = src.binHz` (the snapshot's value while frozen, since the snapshot source carries its own `binHz`). `settings.numPoints` is clamped to `maxVisiblePoints` (the visible count), so the processor, which still sets `numPoints = SpectrumFrame::maxPoints` (now 3072), keeps getting 2048 visible points and a bit-identical Fit frame.
