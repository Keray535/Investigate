## 2. Spectrum display techniques

**Window coherent-gain correction.** A window's coherent gain (CG) is the mean of its sample values; dividing the FFT magnitude by `CG × N` (or, equivalently, normalizing the window to unit CG before applying it) makes a full-scale sine read 0 dBFS at its peak bin, provided the bin lands exactly on the tone (worst case is scalloping loss, next point). Standard scalloping-loss and CG figures (from the classic Harris 1978 windowing survey, reproduced in many DSP texts and the NI/Keysight windowing app notes):

| Window | Coherent gain | Scalloping loss (worst-case bin-straddle amplitude error) |
|---|---|---|
| Rectangular | 1.0 | 3.92 dB |
| Hann | 0.5 | 1.42 dB |
| Hamming | 0.54 | 1.78 dB |
| 4-term Blackman-Harris | ≈0.36 | ≈0.83 dB |
| Flat-top | ≈0.215–0.22 (implementation-dependent) | <0.01 dB (flat-top is designed specifically to minimize this) |

Source for the standard figures and the underlying theory: F. J. Harris, "On the Use of Windows for Harmonic Analysis with the Discrete Fourier Transform," *Proc. IEEE*, 66(1), 1978 (the canonical citation used by virtually all spectrum-analyzer window tables); cross-checked against Julius O. Smith III's online DSP text, ["Spectrum Analysis Windows"](https://ccrma.stanford.edu/~jos/sasp/), which restates CG-normalization and scalloping loss with the same definitions.

**Power vs. dB averaging.** Average in the power (linear-squared magnitude) domain, not in dB, before the final `10*log10`. Averaging already-converted dB values biases the result low for anything but pure tones (Jensen's inequality on the concave `log` function), because dB-averaging under-weights transient peaks relative to power-averaging. Use exponential (single-pole IIR) averaging: `p_avg[n] = α·p_new + (1-α)·p_avg[n-1]`, with `α = 1 - exp(-Δt / τ)` where `Δt` is the hop time and `τ` is the user's averaging-time parameter, so the effective time constant stays correct when the hop size changes with FFT size/overlap. This is the standard technique described in real-time spectrum analyzer literature (e.g. Ballou, *Handbook for Sound Engineers*, "Real-Time Analyzers" chapter) and matches SPAN-style "Averaging" controls researched in T-001.

**Bin-to-display-point mapping.** Below roughly bin-spacing-equals-pixel-spacing (low frequencies, where log-spaced display points are denser than linear FFT bins): linearly interpolate magnitude (in power domain) between the two bracketing bins. Above that crossover (high frequencies, many bins per display point): aggregate with either peak-hold (never miss a narrow peak — SPAN's default visual style) or an RMS/power-mean across all bins that fall in a display point's frequency span. This dual strategy (interpolate where sparse, aggregate where dense) is the standard approach in real-time analyzers and is explicitly implemented this way in the JUCE spectrum tutorial referenced below.

**Fractional-octave smoothing.** Hatziantoniou & Mourjopoulos, "Generalized Fractional-Octave Smoothing of Audio and Acoustic Responses," *J. Audio Eng. Soc.*, 48(4), pp. 259–280, April 2000 ([AES E-Library entry](https://aes2.org/publications/elibrary-page/?id=12070); overview also in the follow-up "Addendum," [Semantic Scholar](https://www.semanticscholar.org/paper/Addendum-to-'Generalized-Fractional-Octave-of-Audio-Hatziantoniou-Mourjopoulos/1871be5212eba2c331b1e51821ba7f6166947840)) defines a frequency-domain convolution with an analytically-derived window whose width in bins grows proportionally with center frequency for a constant `1/N`-octave bandwidth, applied directly on the (log or linear) FFT magnitude/power array without needing to resample to a log axis first. This generalizes the older method (interpolate to log-frequency, apply constant-width smoothing, interpolate back) and preserves symmetry. Recommend implementing the direct log-domain moving average (per display point, average over `±(1/(2·N))` octave of neighboring points in the *already log-mapped* display array) as the pragmatic simplification, since `SpectrumMapper` already produces a log-spaced point array — this avoids a second bin-domain smoothing pass and is functionally equivalent once points are log-spaced with power-domain values.

**Slope/tilt.** Apply as `+slope_dB_per_octave × log2(f / 1kHz)` added post-smoothing, pre-final-dB-clamp, matching SPAN's "Slope" control (1 kHz pivot per the roadmap's parameter table) — this is a simple per-point additive term, not a filter.

**Reference implementations (ideas/license only, nothing to copy):**
- JUCE official spectrum analyser tutorial: [Tutorial: Visualize the frequency response of your plugin (JUCE docs)](https://docs.juce.com) — JUCE example code, JUCE's own module license; safe to read for approach, not to copy verbatim without complying with JUCE's example-code terms.
- ffAudio Frequalizer (Foleys, open source, **GPLv3** — ideas only, must not be copied into this GPL-incompatible product).

**Recommendation:** power-domain exponential averaging with `α` derived from hop time and the `avgTime` parameter; bin→point mapping with linear interpolation below the crossover and peak/power-mean aggregation above it; fractional-octave smoothing as a log-domain moving average over the already-mapped display points, modeled on Hatziantoniou & Mourjopoulos (2000); coherent-gain-normalize every window so a full-scale sine reads 0 dBFS.

## 3. Loudness (ITU-R BS.1770-4/-5, EBU R128)

**K-weighting coefficients at 48 kHz** (biquad cascade: Stage 1 = pre-filter/high-shelf, Stage 2 = RLB high-pass), quoted to the standard's published precision:

- Stage 1 (shelf): `b0 = 1.53512485958697`, `b1 = -2.69169618940638`, `b2 = 1.19839281085285`, `a1 = -1.69065929318241`, `a2 = 0.73248077421585`
- Stage 2 (high-pass): `b0 = 1.0`, `b1 = -2.0`, `b2 = 1.0`, `a1 = -1.99004745483398`, `a2 = 0.99007225036621`

These are the values published in ITU-R BS.1770-4 §5/Annex 1 and reproduced identically by the reference implementation libebur128 (`ebur128_filter.c`), which is the de-facto cross-check used across the industry; see the library and its accuracy discussion at [github.com/jiixyj/libebur128](https://github.com/jiixyj/libebur128). A description of the two-stage structure (shelf + RLB high-pass) and its rationale is also given in the ITU-R BS.1770-4 text itself.

**Deriving coefficients for other sample rates.** BS.1770 only tabulates 48 kHz values; libebur128's approach — confirmed by reading its filter-construction code and used as the standard technique cited across implementations — is to treat the 48 kHz digital biquad as a matched approximation of an underlying analog K-weighting prototype, then re-derive digital coefficients for the target rate via the bilinear transform of that analog prototype (equivalently, warp the pole/zero locations for the new `fs`). An accuracy evaluation across implementations, including the sample-rate-adaptation question, is given in Brecht De Man & Josh Reiss's ["A study of loudness measurement algorithm accuracy"](https://www.researchgate.net/) style comparisons and, more concretely, in EBU Tech 3341's own accuracy discussion — the practical takeaway for T-006 is: **do not linearly resample the fixed 48 kHz coefficients**; re-derive from the analog prototype per sample rate (44.1–192 kHz), as libebur128 does, or resample the input to 48 kHz internally before filtering (a valid, simpler engineering alternative used by several meters, at the cost of an extra resampling stage). Recommend the resample-to-48kHz approach for engineering simplicity given the project's budgets, since BS.1770 itself notes the filter response is not overly sensitive to minor rate mismatches within normal music-production rates — flag this as an implementation choice for T-006 to validate against the EBU test cases either way.

**Momentary/short-term windows and gating.** Momentary loudness: 400 ms window, updated at least every 100 ms (i.e., in 100 ms overlapping blocks). Short-term loudness: 3 s window, same 100 ms update granularity. Integrated (gated) loudness per BS.1770 Annex 2 / EBU R128: compute mean-square per 400 ms gating block (100 ms hop); apply **absolute gate** at −70 LUFS (discard blocks quieter than this); compute the ungated mean, then apply **relative gate** at (ungated mean − 10 dB), discard blocks below that, and average what remains for the integrated value.

**Real-time-safe histogram.** Use a fixed-size histogram over LUFS quantized to a fixed step (libebur128 uses 0.1 LU steps from about −70 to 5 LUFS = ~751 bins) with a running sum-of-block-loudness and count per bin, so both gating passes and LRA percentiles are O(1) additional memory and O(bins) time — no dynamic allocation on the audio thread, satisfying the CLAUDE.md real-time rules. This is exactly libebur128's approach (histogram mode, as opposed to storing every block).

**LRA (EBU Tech 3342).** Compute 3 s short-term loudness values (100 ms hop) over a program; gate with the same absolute (−70 LUFS) and a relative gate at (ungated short-term mean − 20 dB, per Tech 3342, *not* the −10 dB used for integrated loudness); LRA = 95th percentile − 10th percentile of the remaining short-term values, in LU. Source: [EBU Tech 3342 PDF](https://tech.ebu.ch/files/live/sites/tech/files/shared/tech/tech3342v2_0.pdf).

**EBU Tech 3341/3342 test cases.**

**Recommendation:** implement K-weighting exactly as tabulated above at 48 kHz; internally resample to 48 kHz for other project sample rates as the simplest correctness-first strategy, and validate against both the synthesizable Tech 3341 sine cases and libebur128 as a cross-check; download the official EBU test set into a gitignored test-fixtures path for the true-peak/LRA cases that need exact source audio.

## 4. True peak

BS.1770-5 Annex 2 (Attachment 1) specifies a **4× oversampling** measurement via a **48-tap, 4-phase polyphase FIR** (i.e., 4 sub-filters of 12 taps each) derived from a windowed-sinc interpolation filter designed so that any compliant meter converges on the same true-peak estimate; ITU republishes the exact tap values in the recommendation text itself: [ITU-R BS.1770-5 (11/2023) PDF](https://www.itu.int/dms_pubrec/itu-r/rec/bs/R-REC-BS.1770-5-202311-I!!PDF-E.pdf), Annex 2. **License of the coefficients: none required** — they are numeric constants published in a normative ITU-R recommendation; ITU text/figures carry ITU's own copyright on the *document*, but the numeric filter taps, quoted with attribution to the Recommendation, are standard practice industry-wide (this is how libebur128, ffmpeg's `ebur128`, and every commercial loudness meter derive their true-peak filter) and are not "code" in a licensable sense — quote them directly from the ITU PDF, with citation, rather than copying any third party's C reimplementation.

**Oversampling factor by sample rate.** BS.1770 recommends 4× oversampling for the 44.1/48 kHz family. For higher native rates the effective oversampling needed to resolve inter-sample peaks at typical program material is lower relative to Nyquist, and in practice most compliant meters use 4× up to 48 kHz, and 2× (or even 1×, treating the higher native rate as already sufficiently oversampled) at 96/192 kHz — libebur128 and ffmpeg both branch: 4× at ≤48 kHz (192 kHz internal), 2× at 96 kHz sample rate ranges, and 1× (no oversampling) above roughly 192 kHz already-native. **Recommendation for T-007:** oversampling factor 4 at 44.1/48 kHz, 2 at 88.2/96 kHz, 1 (no oversampling, direct sample peak) at 176.4/192 kHz — matching the common libebur128/ffmpeg convention, to be confirmed against the Tech 3341 true-peak test cases in section 3's table.

**Tech 3341 true-peak tolerances.** Tech 3341 states an acceptable true-peak measurement tolerance of approximately **±0.2 dB** relative to the reference values in its true-peak test cases (some cases quote up to ±0.4 dB depending on the specific aliasing pattern under test) — see [tech3341v2_0.pdf](https://tech.ebu.ch/docs/tech/tech3341v2_0.pdf), Annex 2 test-case table.

**Recommendation:** implement the ITU-R BS.1770-5 Annex 2 48-tap/4-phase polyphase FIR directly from the published coefficients, sample-rate-dependent oversampling factor (4/2/1 as above), and validate against Tech 3341's true-peak cases at their stated tolerance.

## 5. Correlation meter

Formula: normalized cross-correlation (Pearson correlation coefficient) of the L/R signal over an integration window:

```
corr = Σ(L·R) / sqrt(Σ(L²) · Σ(R²))
```

computed either as a true sliding sum (memory = window length in samples) or, more commonly in real-time meters, as three single-pole exponentially-smoothed running sums (`ΣLR`, `ΣL²`, `ΣR²`) with a time constant giving the desired integration feel — the exponential form avoids the sliding-window memory cost and is the standard technique for hardware/software correlation meters. Typical integration times in the literature and in commercial meters range **~300–600 ms** (Sound On Sound's phase-meter explainer cites ~600 ms as a common choice: [SOS "What are my phase-correlation meters telling me?"](https://www.soundonsound.com/sound-advice/q-what-are-my-phase-correlation-meters-telling-me)); the roadmap's provisional ~300 ms is within the normal range and should be confirmed against SPAN's actual behavior by T-001.

**Silence handling:** when `ΣL²·ΣR²` underflows to ~0 (near-digital-silence), the division is undefined/noisy — clamp the denominator to a small epsilon or hold the last valid reading (freeze display) rather than let a near-zero denominator produce a wildly oscillating correlation value. This matches common commercial-meter behavior (holding last value or centering at 0 during silence).

**Mono handling:** if the channel mode reduces to a single channel (Mid-only, or mono host input), correlation is undefined/meaningless for a single channel — display as fixed +1 (perfectly correlated with itself) or hide the meter; the `MeterSnapshot.isMono` flag already planned in the roadmap should drive this in the editor.

**Recommendation:** exponentially-smoothed running sums with an integration time constant ≈300 ms (to be confirmed by T-001 against SPAN), epsilon-clamped denominator, and `isMono` short-circuits to +1 in the snapshot/editor.

## 6. K-system and RMS

**K-system reference levels (Bob Katz):** K-20 (0 dBFS = +20 dB above reference, wide dynamic-range mastering), K-14 (0 dBFS = +14 dB above reference, broadcast/typical pop), K-12 (0 dBFS = +12 dB above reference, loudness-limited/broadcast). In each system the meter's "0" mark (analogous to VU 0) sits at −20/−14/−12 dBFS respectively, and the meter is calibrated so a sine tone at that reference level reads 0 VU-equivalent. This is Bob Katz's own published system (widely reproduced; see K-System entries in mastering-engineering references and Katz's *Mastering Audio* book) — for this project it reduces to a display-only offset applied in the editor per the roadmap's `MeterSnapshot` note ("the editor applies... the K-system reference when meterScale is K-20/K-14/K-12"), i.e. `displayed_dB = dBFS_value + K_offset` where `K_offset` is 20, 14, or 12.

**AES17 sine-referenced RMS +3.01 dB offset.** AES17 defines RMS meter calibration such that a full-scale sine wave (peak = 0 dBFS) reads **0 dBFS on the RMS scale** despite its RMS value being 3.0103 dB below its peak (since `RMS = peak/√2` for a sine, and `20·log10(√2) = 3.0103 dB`). So AES17-style "sine-referenced" RMS meters add a fixed +3.0103 dB to the raw computed RMS-in-dBFS value before display. The roadmap already notes this exact detail: "RMS is not sine-referenced [internally]... the editor applies the +3.01 dB AES17 offset." Source: AES17-2015 (AES standard for digital audio measurement) definition of RMS-referenced full-scale, widely restated in professional audio metering literature.

**Sliding-window vs. exponential RMS.** A true sliding-window RMS requires a running sum of squares over exactly `windowMs` of samples, which needs a ring buffer of squared samples sized for the window (memory scales with sample rate × window length); exponential RMS (single-pole low-pass on the squared signal) needs only one running accumulator per channel but the "window" is only an approximate equivalent time constant, and its step response is not a sharp cutoff. **Memory for a 3000 ms sliding window at 192 kHz, stereo:** `3.0 s × 192000 samples/s × 2 channels × 4 bytes (float) = 4,608,000 bytes ≈ 4.4 MiB` for the raw ring buffer (or half that, ~2.2 MiB, if squared values are pre-summed incrementally with only sample history retained, since you still need every sample in the window to subtract on slide-out). This is comfortably inside the project's 64 MB per-instance budget even with both a sliding RMS ring buffer and everything else, so a true sliding window is affordable at the worst-case `rmsWindow` = 3000 ms and 192 kHz.

**Recommendation:** implement RMS as a true sliding-window sum-of-squares (ring buffer sized for max `rmsWindow` × max sample rate, allocated in `prepare`), since the memory cost (~4.4 MB stereo worst case) is small relative to budget and gives an exact, parameter-matching window rather than an approximate time constant; apply the +3.01 dB AES17 offset and the K-system additive offset only at display time in the editor, never on the audio thread's raw dBFS value.

## 7. Lock-free exchange

**SPSC ring buffer.** `juce::AbstractFifo` is the standard JUCE SPSC pattern: the producer calls `prepareToWrite`, writes into the returned index ranges, then `finishedWrite`; the consumer mirrors with `prepareToRead`/`finishedRead`. It internally uses `std::atomic<int>` read/write cursors with correct acquire/release semantics, is allocation-free once sized, and is exactly the shape needed for `SampleFifo` (producer = audio thread pushing samples, consumer = analysis thread popping). Documented in JUCE's own class reference and used pervasively in JUCE example code (e.g. the official audio-thread-to-message-thread FIFO patterns in JUCE demos). For multichannel float sample data, wrap N `AbstractFifo`s (one per channel) sharing one cursor pair, or a single `AbstractFifo` over an interleaved/de-interleaved flat buffer — either is real-time-safe as long as the buffer is sized once in `prepare` and never resized on the audio thread.

**Triple buffer for fixed-size frames.** A lock-free triple buffer (a well-known pattern, e.g. described by Remis Le Louarn / "Triple Buffering as a Concurrency Mechanism" and used throughout real-time audio/graphics code) uses three fixed-size buffer slots and one atomic "which slot is newest" index (packed with dirty/available bits, typically in a single `std::atomic<uint8_t>` or `uint32_t` using compare-and-swap). Producer writes into a private "write" slot, then atomically swaps it with the shared "ready" slot (release semantics); consumer atomically swaps the shared "ready" slot into its own "read" slot (acquire semantics) whenever it wants the latest frame, never blocking the producer and never missing a frame's worth of memory safety, at the cost of possibly skipping intermediate frames (acceptable here since only the newest `SpectrumFrame` matters to the editor). This matches the roadmap's `FrameExchange` (analysis → message thread) requirement exactly.

**Meter snapshot via atomics.** Since `MeterSnapshot` (per the roadmap) is a POD-like struct of plain numeric fields, the simplest correct real-time-safe publish pattern is **not** a single large atomic struct (most `MeterSnapshot`-sized structs exceed lock-free hardware CAS width) but either: (a) a double-buffered pair of snapshots with one `std::atomic<int>` index published with `memory_order_release` by the writer and read with `memory_order_acquire` by any reader (a two-slot version of the triple-buffer idea, sufficient here because the audio thread is the sole writer and reads are tear-free once the index swap is acquire/release-ordered), or (b) per-field `std::atomic<float>`/`std::atomic<int>` if approximate cross-tearing between fields in a single read is acceptable (it usually is for meters, since each field is independently displayed). Recommend (a): a double-buffered snapshot with acquire/release index publish, giving both a fully torn-free consistent snapshot and no locks. This is the standard "seqlock-free" double-buffer approach documented in numerous lock-free programming references (e.g. Jeff Preshing's "An Introduction to Lock-Free Programming" blog, widely cited for exactly this acquire/release double-buffer pattern).

**Recommendation:** `juce::AbstractFifo`-based SPSC ring buffer for `SampleFifo`; a hand-rolled lock-free triple buffer (single atomic slot-index with CAS) for `FrameExchange`; a double-buffered `MeterSnapshot` with `memory_order_release` on publish / `memory_order_acquire` on read for `MeterBank`'s publish path.

## 8. JUCE 8 rendering on Windows

**Direct2D renderer.** JUCE 8 makes Direct2D the default Windows renderer, moving path rasterization off the CPU onto the GPU, which JUCE's own announcement frames as the primary performance win over the legacy software renderer for filled-path-heavy UIs: [JUCE 8 Feature Overview: Direct 2D](https://juce.com/blog/juce-8-feature-overview-direct-2d/). Forum performance threads report continued tuning through 8.0.x, including a change where a CPU-side image buffer became the "source of truth" for JUCE Images (rather than the GPU texture) to fix correctness/perf edge cases, and note that heavy multi-window scenarios can still see slowdowns: [Direct2D performance questions](https://forum.juce.com/t/direct2d-performance-questions/64255). For a single analyser window painting one dense spectrum path plus a grid at 60 fps (this project's shape), Direct2D should comfortably beat the software renderer, but the roadmap's own risk #1 (dense filled paths at high DPI) should still be profiled directly, since forum reports are about JUCE in general, not this project's specific paint load.

**`juce::VBlankAttachment`.** The roadmap's design (editor repaint driven by `VBlankAttachment`) is JUCE's recommended mechanism for tying repaints to the monitor's actual refresh rate rather than a fixed `Timer` interval, avoiding tearing/over-painting and reducing wasted CPU when the display can't keep up — this is JUCE's documented replacement for ad hoc `startTimerHz(60)` repaint loops.

**OpenGL context in JUCE 8.** Forum discussion flags that attaching an `OpenGLContext` to a top-level component can conflict with or override the default Direct2D renderer choice, and there are open bug threads about Direct2D/OpenGL interaction on Windows in JUCE 8: [Handling Direct2D and OpenGLContext Together](https://forum.juce.com/t/handling-direct2d-and-openglcontext-together/62697), [OpenGL rendering issues with latest JUCE 8 develop on Windows](https://forum.juce.com/t/bug-opengl-rendering-issues-with-latest-juce-8-develop-on-windows/62599). Net: OpenGL is a viable fallback (per the roadmap's risk #1 mitigation) but is not free of its own JUCE-8-specific rough edges on Windows as of this research date, and mixing it with Direct2D specifically is the risky combination — if T-012 needs the OpenGL fallback, it should replace Direct2D for that window rather than layer both.

**Caching strategies.** Cache the static grid/axis labels as a pre-rendered `juce::Image` (redrawn only when the frequency/dB range or window size changes, not every frame) and reduce the spectrum curve to roughly one point per pixel column before building the `Path` (already in the roadmap's risk mitigation) — both are standard JUCE performance practices repeated across forum performance threads and the JUCE tutorials on efficient painting.

**Recommendation:** keep Direct2D as the default renderer, drive repaints with `VBlankAttachment`, cache the grid as an image, and reserve OpenGL strictly as a documented fallback (not combined with Direct2D) if the paint budget in T-012 is missed.

## 9. Standalone input

The JUCE Standalone wrapper's `StandalonePluginHolder` exposes a **"Mute audio input"** toggle (backed by `getMuteInputValue()`, a `juce::Value` bound to a checkbox JUCE places in the Standalone's audio-settings UI) that defaults to **muted (on)** specifically to prevent feedback loops when a plugin's output is audible and its input is also live (e.g. a synth or an effect that could otherwise route mic/loopback input straight to speakers) — see the `StandalonePluginHolder` reference (documented via the mirrored class docs at [ccrma.stanford.edu/~jos/juce_modules/classStandalonePluginHolder.html](https://ccrma.stanford.edu/~jos/juce_modules/classStandalonePluginHolder.html)) and JUCE forum reports of the same default behavior, e.g. [Standalone plugin does not receive audio input (macOS)](https://forum.juce.com/t/standalone-plugin-does-not-receive-audio-input-macos/34687).

For an analyser like Investigate, the plugin's own output is always the input passed through bit-exact (per the roadmap's zero-latency pass-through design), so there is no feedback risk from analyzing live input while also outputting it — the "mute input" default exists for the general case (synths, generators) and is not actually needed here, but it still ships on by default in the generic Standalone template. **Configuration guidance for T-008/T-009 (per roadmap risk #7):** either (a) programmatically uncheck "Mute audio input" on first run via `StandalonePluginHolder::getMuteInputValue().setValue(false)` when constructing the Standalone's options, or (b) document in the app that users should uncheck it themselves in the audio-settings panel — (a) is preferable for out-of-the-box UX since the analyser is useless with muted input, and there is no feedback risk to justify defaulting to muted for a pass-through effect.

**Recommendation:** set the Standalone's default `muteInput` value to `false` in the plugin's `createStandaloneOptions` / `StandaloneFilterApp` configuration (T-008/T-009), since Investigate's zero-latency pass-through design carries no feedback risk that the mute-input default is meant to guard against.
